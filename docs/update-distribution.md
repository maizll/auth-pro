# 在线更新分发（内部）

这份说明只给维护源站的人。不要放进官网文档。

同一份 1.7.1 发两次，版本号相同。一次在 `maizll/auth-pro-client`，官网的分发接口从这里取客户包。一次同步到 `maizll/auth-pro` 的 Release。官网自己从后者更新。1.7.0 及更早的客户也只认识后者，所以他们从那里一次升到 1.7.1。老客户都升完以后，`maizll/auth-pro` 改为私有。改成私有之后，官网用存储管理里的令牌继续更新。

## 怎么认出官网

官网和客户站是同一份程序。数据目录 `store/snapshot-ed25519.key` 的前 32 字节当种子重算公钥，必须等于编译进程序的公钥 `pwAizm/sOyWCu+qi8+Dl/xJr0Upuamh5u7vL3wGT14A=`，文件后 32 字节也必须是这个公钥，这台机器才算官网。不能只看后 32 字节：那一段可以照抄公开的公钥。文件不存在、读失败、内容损坏，或公钥对不上，都按客户站处理。只看到文件还不够。

## 客户站

1.7.1 及以后、没有这把私钥的站点只向下面三个地址要更新：

```text
https://auth.maizll.com/api/v1/update/latest.json
https://auth.maizll.com/api/v1/update/releases.json
https://auth.maizll.com/api/v1/update/package/<版本号>
```

后台不能改地址。环境变量 `AUTO_PRO_UPDATE_URL` 不再起作用。数据库里如果还存着旧的更新地址（含 `api.github.com/repos/`、`github.com/*/releases/`、`raw.githubusercontent.com/`），进程启动时会删掉。

## 官网自己更新

不设环境变量时，官网从 `maizll/auth-pro` 的 Release 取 `latest.json`。服务器上可以用 `AUTO_PRO_OFFICIAL_UPDATE_REPOSITORY` 改成别的 `owner/repo`。格式不对时接口只返回「更新仓库未配置」，不回显这段配置。

官网读这个仓库时依次试：软件源设置里的收费仓库令牌、存储管理里各个 GitHub 存储的令牌、Release 设置里的令牌，最后匿名。用上哪个就在「在线更新」页的「更新来源」一行里写出来（「更新来源正常（用的是存储「X」的令牌）」）；读不到时这一行用灰字写原因，不报红。客户站没有这一行。

1.8.5–1.8.7 有过一个单独的「官网更新令牌」（数据目录 `store/official-update-token`）。1.8.8 起不再使用，升级后第一次启动会删掉这个文件和它的密钥，并给超级管理员发一条通知。理由：它是只读令牌，放进存储管理会一直被存储检查报「没有写入权限」；统一一套令牌顺序后，存储管理里的令牌加上本仓库就能读；删的时候仓库仍是公开的，匿名照样能更新，不会断。

存储管理的「存储检查」里有一行「官网更新来源」：仓库公开时是灰色提醒，私有时写出能读它的令牌，读不到时报问题并通知超级管理员。

发布工作流 `release.yml` 用工作流自带的令牌下载上一版的 `releases.json`，私有仓库照样能读。下载失败时工作流直接停下，不会生成丢了历史版本的记录。

后台拿到的清单会去掉下载地址。页面上看不到仓库地址。

## 更新包签名（1.8.6 起）

`latest.json` 里的 `signature` 一直只是 `sha256:` 加包哈希，和 `sha256` 字段是同一个值，不是签名。1.8.5 及更早的站点要求这个字段存在且等于它，所以发布时照旧写。

真正的签名在安装包里面：`manifest.json` 多了 `files`（包内每个文件的 SHA256）和 `signature`（`ed25519:` 加签名）。签名覆盖版本号、安装路径和全部文件哈希（规范化文本见 `backend/updatesign`）。打包时 `scripts/build-release.sh` 调 `backend/cmd/release-sign manifest` 写清单，环境变量 `AUTH_PRO_UPDATE_SIGNING_KEY` 有私钥就签名。`release.yml` 从仓库机密 `AUTH_PRO_UPDATE_SIGNING_KEY` 取私钥，没配置就失败；打完包再用 `release-sign verify` 按内置公钥核对一次。服务端和客户端两个仓库都要配这个机密，值相同。

程序内置公钥（`updatesign.PublicKey`）。1.8.6 起的官网和客户站在线更新下载完、解压之前验签：没签名、不是这把私钥签的、签完又改过（改、加、删任何文件，或把旧版本的包改成新版本号），都拒绝安装，删掉下载的包，页面提示「没有通过官方签名校验……网站没有任何改动」。官网只原样存储和转发安装包，不参与签名，`latest.json` 的格式不变。

1.8.5 及更早的站点不认识这两个新字段，解析时忽略，仍按旧规则升级到 1.8.6；升到 1.8.6 之后再往后升级就强制验签。因此「从仓库导入」或手动上传给客户的安装包，必须是发布工作流打出来的原包，不能解开重打。

换私钥要发一版带新公钥的程序，并且这一版仍用旧私钥签名，客户站才能装上它。

## 分发给客户

1.7.2 起，上面三个地址只读官网应用「授权系统」（`app_f93896d80066_5811`）的发布版本。不再在对外接口里连接代码托管站。下载地址一律写成 `https://auth.maizll.com/api/v1/update/package/<版本号>`，清单里的 SHA256 和大小按磁盘上的安装包计算，`signature` 仍是 `sha256:` 加上同一个哈希。文件名仍是 `auth_pro-full-v<版本>.tar.gz`。说明里如果带有托管站地址，会在返回前删掉。

`latest.json` 和 `releases.json` 缓存大约 3 分钟，保存发布版本后清掉。同一 IP 每分钟最多 30 次清单请求、6 次安装包下载。

后台「发布版本」里的「从仓库导入」只读该应用已经绑定的私有仓库，不再使用写死的默认仓库。`AUTO_PRO_UPDATE_REPOSITORY` 只在官网升级迁入客户安装包时作为来源，不改变客户站请求的地址，也不拿去改官网自己的更新来源。开发者端不挂这组导入接口。开发者上传的收费包仍由本站用站长令牌写入该应用绑定的仓库。登记外链时只从公开 https 下载，下载请求不带站长令牌。

## 老客户怎么升上来

1.7.0 默认读取 `maizll/auth-pro` 最新 Release 里的 `latest.json`。清单字段没有改：安装包地址在该仓库的 Release 下，`sha256` 是包的哈希，`signature` 是 `sha256:` 加上同一个哈希，文件名是 `auth_pro-full-v<版本>.tar.gz`。在 `maizll/auth-pro` 上打 1.7.1 的标签后，1.7.0 按这套规则安装。安装时它还会向该仓库核对附件摘要，摘要就是这个包的 SHA256。

装上 1.7.1 之后，没有签名私钥的站点自动只向官网要更新，客户不用改配置。

## 仓库改私有当天

存储检查里「官网更新来源」那行的「改为私有」按钮不会直接改这个仓库，只打开下面的步骤，并自动检查存储管理里现有的令牌改私有后能不能读。

1. 先确认已经没有 1.7.0 及更早的客户站。它们直接读本仓库的 Release，改私有后就收不到更新。`latest.json` 里的安装包地址仍指向本仓库，也是为了它们；1.7.1 及以后的客户站只读官网改写过的清单，看不到这个地址。
2. 在官网「存储检查」点「官网更新来源」那行的「改为私有」，看令牌检查结果。经典令牌带 `repo` 权限会显示「改私有后能读」。细粒度令牌在仓库公开时无法确认，会提示去确认它在 Repository access 里选中了 `maizll/auth-pro`。细粒度令牌的权限对所选仓库一视同仁，存储用的 Contents 读写也会作用到本仓库；介意的话另建一个只选本仓库、Contents 只读的令牌，填进软件源「Release 设置」。
3. 检查结果显示没有能读的令牌时，先按提示补上，再回来检查。
4. 在仓库设置里把可见性改成私有。
5. 回官网点「立即检查」，「官网更新来源」那行应写「是私有仓库，用存储「X」的令牌可以读取」。再到「在线更新」点「检查更新」，「更新来源」一行应显示「更新来源正常（用的是存储「X」的令牌）」。
6. 用 `curl -fsS https://auth.maizll.com/api/v1/update/latest.json` 确认客户站的更新清单照常返回。客户站不连代码托管站，不受影响。
7. 下一次打标签发布时看一眼 `release.yml` 是否全绿。它用工作流自带的令牌，不用另外配置。本机的发布核对脚本如果用匿名下载附件，要改成带登录态下载。
8. 令牌过期前在存储管理里换新的。过期后存储检查会报「官网更新来源读不到」并通知超级管理员，客户站不受影响。
