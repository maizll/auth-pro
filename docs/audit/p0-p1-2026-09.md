# P0 / P1 审计（2026-09）

本文是 **v1.5.0 当时** 的只读审计记录，正文保留发现时的证据，不改写成「已经修好」。后续版本的修复见 [安全说明](../security.md) 与根目录 `CHANGELOG.md`（v1.5.1 起）。采购与运维以安全说明和当前代码为准，不要把下面的「影响」当成 1.5.5 仍未处理的漏洞清单。

范围说明（写作时）：当时的 `master`（产品 v1.5.0）。本文只记录已在本仓库核对过的问题，不包含修复。写作时版本号、Release、tag 均未改。

严重级别：

- **P0**：未授权即可接管或清库，或并发下可以多拿授权 / 少扣余额。
- **P1**：已登录角色可以越权、通知与告警会误导运维、更新或拉取链路信任不足、密钥文件权限过宽。

## P0

### P0-01 安装锁丢失后，未登录即可清库并新建超级管理员

- **证据**
  - `backend/middleware/install_guard.go`：已安装只看 `install.lock`。锁不存在时，带空 `Origin` 的请求（curl）直接放行。
  - `backend/handler/install.go` `InstallInitTables` 对请求里的数据库执行嵌入的 `schemaSQL`。
  - `backend/handler/schema.sql` 开头是 `SET FOREIGN_KEY_CHECKS = 0`，随后对 `admins`、`licenses` 等表 `DROP TABLE IF EXISTS` 再重建。
  - 同文件 `InstallCreateAdmin` 用 `config.LoadDBConfig()`（即已有的 `db.json`）连接，再 `INSERT INTO admins ... role_id = 1`。不检查是否已有管理员。
  - `backend/config/config.go` `CreateLockFile` 才写锁。锁文件和数据库是两套状态。
- **影响**
  - 锁文件被删、漏拷贝或只恢复了数据库时，安装写接口重新打开。
  - `InstallCreateAdmin` 不使用请求体里的数据库账号，而是读服务器上的 `db.json`。远程调用者不需要知道数据库口令，只要锁不在、配置文件还在，就可以 `POST /api/install/create-admin` 插入另一个 `role_id = 1` 的超级管理员（用户名不冲突即可）。
  - `POST /api/install/init-tables` 会执行整库 `DROP TABLE`，但口令来自请求体。本地其它用户若能读到 `db.json`（见 P1-08），就可以带上这些口令把库清掉再走上面的建管理员步骤。只从公网调用、又不知道数据库口令的人，单靠这个接口清不了库。
- **修复形状**
  - 锁缺失时，若库里已有 `admins` 或业务表，拒绝 `init-tables` / `create-admin`，要求持有已有管理员凭证或一次性恢复口令。
  - `schema.sql` 只允许空库执行；非空库走版本化迁移，禁止整库 `DROP TABLE`。
- **建议测试**
  - 有 `install.lock` 时两个写接口返回 403。
  - 无锁但 `db.json` 和 `admins` 已存在时，`create-admin` 返回 403，且 `admins` 行数不变。
  - 无锁、库非空时，`init-tables` 不得执行 `DROP TABLE`。
  - 空库且无锁时，原安装流程仍能完成。

### P0-02 余额购买用「事务外读到的余额」做绝对值回写，并发会少扣或多发授权

- **证据**
  - `backend/handler/user_panel.go` `UserPurchase`：在 `db.Begin()` 之前 `SELECT balance`，事务内执行 `UPDATE users SET balance = ? WHERE id = ? AND balance >= ?`，`?` 是事务外算好的 `balance - cost`。只判断 `err`，不看 `RowsAffected`。随后仍 `INSERT INTO licenses`。
  - `backend/handler/agent_panel.go` `AgentPanelPurchase`：同样在事务外读代理余额，再 `SET balance = ?`。这里检查了 `RowsAffected == 0`，但条件只是 `balance >= cost`，不是「当前余额仍等于刚才读到的值」。
  - 充值入账 `increaseSubjectBalance`（`backend/handler/epay.go`）用的是 `balance = balance + ?`，购买扣款没有用同一写法。
- **影响**
  - 用户并发两笔余额购买：后一笔 `UPDATE` 影响 0 行时仍会插入授权，等于不扣款发证。
  - 代理两笔不同金额：先扣成 40 的事务提交后，后一笔仍可能因 `40 >= 较小金额` 成功，并把余额写成自己事务外算的旧值（例如 70），把前一笔扣款盖掉。两张授权都发出去。
- **修复形状**
  - 在同一事务里 `SELECT balance ... FOR UPDATE`，用 `UPDATE ... SET balance = balance - ? WHERE id = ? AND balance >= ?`，`RowsAffected != 1` 则回滚。
  - 用户、代理两条购买路径一起改。
- **建议测试**
  - 用可重复的 SQL 假驱动或事务测试库：两笔并发购买，起始余额只够一笔。断言只产生一条 `licenses`，余额只减一次。
  - 两笔金额不同且余额够两笔：最终余额等于起始值减去两笔之和。

## P1

### P1-01 公开授权校验没有频率限制，失败原因可被用来打日志和探测

- **证据**
  - `backend/main.go` 将 `POST /api/license/verify` 放在登录中间件之外。
  - `backend/handler/license_verify.go` `LicenseVerify`：先按 `app_key` 查库，不存在就返回「应用不存在或已禁用」。签名失败、授权无效等各自写一条 `verify_logs`，并返回不同 `reason`。全路径没有令牌桶或 IP 限制。
  - 卡密兑换有限制（`backend/handler/license_card.go` `licenseCardRedeemLimiter`），校验接口没有对等实现。
  - HTTP 状态多数是 200，业务码在 JSON `code` 里。这是现有 SDK 契约，本身不是漏洞。`apps.app_key` 在 `schema.sql` 里标明对外公开，单靠「应用不存在」不能算出 `app_secret`。
- **影响**
  - 知道或扫到 `app_key` 后，可以无限制写 `verify_logs`，把校验日志和数据库打满。
  - 签名通过但授权不存在时，`recordPiracyHit` 还会写 `piracy_records`（需站点打开盗版检测）。
- **修复形状**
  - 按 IP + `app_key` 做滑动窗口，超限返回 429，且不要每条都落库。
  - 应用不存在与签名错误对未持密钥的调用方使用同一对外文案；详细 `reason` 只给签名已通过的请求。
- **建议测试**
  - 同一 IP 连续 N+1 次错误签名，第 N+1 次为 429，且 `verify_logs` 行数不超过 N。

### P1-02 管理员代登录不留审计，并伪装成用户本人登录

- **证据**
  - `backend/main.go`：`POST /user/:id/impersonate`、`POST /agent/:id/impersonate` 挂在 `RequireAdmin()` 下，不是 `RequireSuperAdmin()`。
  - `backend/handler/impersonate.go`：`signImpersonateToken` 的 claims 只有 `user_id` / `username` / `role`，没有代登录标记。用户端有效期 7 天，与普通用户登录同结构。
  - 成功后执行 `UPDATE users/agents SET last_login_at = NOW(), last_login_ip = ?`，IP 取管理员请求的 `ClientIP()`。
  - 仓库里没有把这次操作写入 `operation_logs`。授权卡密等其它管理动作会写该表（`license_card.go`）。
- **影响**
  - 任意后台管理员可以签发与真实用户无法区分的 7 天令牌。
  - 用户「最后登录 IP」被改成管理员出口，事后无法从登录记录分辨代登录。
- **修复形状**
  - 仅 `R_SUPER` 可调用。JWT 增加 `act=impersonation` 与操作者 ID，TTL 缩短到一次排障会话。
  - 写 `operation_logs`（操作者、目标、时间、IP）。不要改目标账号的 `last_login_*`。
- **建议测试**
  - `R_ADMIN` 调用返回 403；`R_SUPER` 成功时 `operation_logs` 有一行，目标 `last_login_ip` 不变。
  - 代登录令牌访问用户接口时，审计中间件能读出真实管理员 ID。

### P1-03 登录签发的 refreshToken 是一枚 7 天管理员令牌

- **证据**
  - `backend/handler/auth.go` `Login`：访问令牌 24 小时。紧接着用同一 `Claims`（`role=admin`、同一 `role_code`）再签一枚 7 天的 `refreshToken`。没有 `typ` 区分。
  - 仓库中没有 `/auth/refresh`。`backend/middleware/jwt.go` `JWTAuth` 接受任何 HMAC 合法、未过期的管理员令牌。
  - 前端 `frontend/src/views/auth/login/index.vue` 把 `refreshToken` 存进 `userStore`。
- **影响**
  - 把响应里的 `refreshToken` 放到 `Authorization: Bearer` 即可使用 7 天，24 小时访问令牌形同虚设。
  - 令牌泄露窗口从 1 天变成 7 天。禁用账号也要到过期才失效（见 P1-04）。
- **修复形状**
  - refresh 令牌单独的 `typ`，`JWTAuth` 拒绝 `typ=refresh`。
  - 刷新接口轮换 refresh，并核对管理员仍启用。
- **建议测试**
  - 用登录返回的 `refreshToken` 调 `GET /api/user/info`，修复后应 401；用访问令牌应 200。

### P1-04 禁用或改角色后，旧管理员令牌仍然有效

- **证据**
  - `Login` 只在签发时查 `admins.enabled = 1` 和 `roles.role_code`。
  - `JWTAuth` 把 `role` / `role_code` 从令牌写入上下文，不再查库。
  - `RequireFreshPassword("admins")` 只比较 `password_changed_at`。禁用账号、修改 `role_id` 都不会改这个时间。
  - 用户端有 `RequireActiveUser` 会复查 `users.enabled`。管理员组没有对等中间件。
- **影响**
  - 被禁用或从超级管理员降权的人，在访问令牌（以及 P1-03 的 7 天令牌）过期前继续调用管理接口。
- **修复形状**
  - 在 `RequireAdmin` 中按 `user_id` 复查 `enabled` 和当前 `role_code`，与令牌不一致则 401。
- **建议测试**
  - 登录后把 `admins.enabled` 设为 0，同一令牌再请求管理接口应 401。
  - 把 `role_id` 从 `R_SUPER` 改成普通角色后，`superSecured` 路由应 403。

### P1-05 菜单权限只在前端生效，普通管理员令牌可调几乎全部管理接口

- **证据**
  - `backend/middleware/jwt.go` `RequireAdmin` 只判断 `role == "admin"`。`RequireSuperAdmin` 只包住系统配置、支付配置、插件源等 `superSecured` 路由（`backend/main.go`）。
  - 授权删除、代登录、用户删除等注册在 `secured` 上，不读 `role_menus`。
  - 中间件目录没有按菜单或权限点鉴权。侧栏来自 `GET /api/system/menus`，那是展示数据。
- **影响**
  - 只分配了部分菜单的后台账号，只要持有管理员 JWT，就可以直接请求未展示的接口，例如 `DELETE /api/license/:id`。
- **修复形状**
  - 为敏感写接口绑定权限点，服务端用 `role_menus` 或等价表拒绝。先覆盖删除、代登录、支付配置以外但仍在 `secured` 上的写操作。
- **建议测试**
  - 建一个没有「授权列表」菜单的管理员角色，其令牌调用 `DELETE /api/license/1` 应 403。超级管理员仍 200。

### P1-06 禁用授权不会通知持有人

- **证据**
  - `backend/handler/license.go` `LicenseToggle` 只执行 `UPDATE licenses SET status = ?`。
  - 下一行注释写明：`TODO(v1.4.x): after SELECT owner_type/owner_id/license_no, call notifyLicenseStatusChanged.`
  - `backend/handler/notification_emit.go` 已有 `notifyLicenseStatusChanged`，此路径没有调用。
- **影响**
  - 管理员把授权打成 `revoked` 后，用户 / 代理收不到站内通知。客户端下次校验才会看到 `license_revoked`。运维以为「禁用即通知」。
- **修复形状**
  - `UPDATE` 成功后查出持有人并调用 `notifyLicenseStatusChanged`。状态未变化时不要重复通知。
- **建议测试**
  - 把一条 active 授权改为 disabled，断言对应用户有一条状态变更通知。重复提交同一状态不再新增。

### P1-07 盗版告警中心的通知设置是空操作，告警表没有写入路径

- **证据**
  - `frontend/src/views/piracy/alerts/index.vue` `handleSaveSettings` 只调用 `ElMessage.success('通知设置已保存')`，没有请求。
  - 全仓库 `INSERT INTO piracy_alerts` 不存在。`backend/handler/piracy.go` 只查询和更新该表。
  - 校验失败时 `recordPiracyHit`（`license_verify.go`）写的是 `piracy_records`，不是 `piracy_alerts`。
  - `isPiracyDetectionEnabled` 默认 false（`system_config.go`）。
  - 仪表盘仍统计 `piracy_alerts WHERE status = 'pending'`（`dashboard.go`），文案是「需要在反盗版模块确认」。
- **影响**
  - 运维打开邮件 / Webhook / 到期提醒并看到「已保存」，实际不会发信、不会回调。
  - 告警列表和仪表盘红点不会因真实盗版命中而增加。盗版追踪页（`piracy_records`）和告警中心是两套数据。
- **修复形状**
  - 要么接上真实配置表和发送器，并在 `recordPiracyHit` 达到阈值时插入 `piracy_alerts`。
  - 要么先去掉保存按钮和仪表盘「待处理盗版告警」，避免显示已生效。
- **建议测试**
  - 保存设置后刷新页面，配置仍在（修复后）。
  - 打开盗版检测并触发 `license_not_found`，告警列表出现对应行，或仪表盘不再引用空表。

### P1-08 数据库口令文件按 0644 写入

- **证据**
  - `backend/config/config.go` `SaveDBConfig`：`os.WriteFile(getConfigPath(), data, 0644)`。内容是主机、库名、用户名、密码的 JSON（`db.json`）。
  - 同文件 `LoadOrCreateJWTSecret` 使用 `0600`。
  - `os.WriteFile` 的权限还会被进程 umask 再收一档。umask `022` 时，结果仍是所有用户可读。
- **影响**
  - 同一主机上的其它系统用户可以读到数据库口令。JWT 密钥文件比它更严，口令文件反而更松。
- **修复形状**
  - `db.json` 改为 `0600`。已存在的文件在启动时 `chmod` 收紧。
- **建议测试**
  - 临时 umask `022` 调用 `SaveDBConfig`，断言文件权限不是其它用户可读。

### P1-09 在线更新不校验签名，非发布目录时直接覆盖正在使用的前端文件

- **证据**
  - `backend/handler/update.go` `executeOnlineUpdate`：`manifest.Package.Signature != ""` 时只写日志「当前版本使用 SHA256 校验」，没有验签。
  - SHA256 与下载地址在同一份 `latest.json` 里。默认清单是 `https://api.github.com/repos/maizll/auth-pro/releases/latest`（`config.go`），GitHub 发布仓库被钉住。自定义 `AUTO_PRO_UPDATE_URL` 时，清单里的 SHA256 就是唯一完整性字段。
  - 解压对绝对路径、`../` 和符号链接会拒绝（`extractOnlineUpdatePackage` 的 `default` 分支）。路径逃逸这条假设不成立。
  - 前端目录不是 `current` 符号链接时，脚本把 `assets` 拷进正在对外服务的目录，然后再换后端二进制（同文件后半段生成的 shell）。
- **影响**
  - 清单来源被替换或镜像被改时，攻击者可以同时改 URL 和 SHA256，签名字段帮不上忙。
  - 拷贝中途失败时，线上前端可以是新旧资源混在一起，而后端还没切换。
- **修复形状**
  - 对 `maizll/auth-pro` 发布物要求独立签名（或 GitHub 发布资产的校验和与仓库签名分开保存），空签名拒绝应用。
  - 前端始终落到新目录再切换符号链接，失败时不改当前目录。
- **建议测试**
  - 清单 SHA256 正确但签名为空或错误时，应用阶段失败。
  - 解压含 `../` 或符号链接的包失败（现有用例可保留）。
  - 模拟拷贝失败后，原 `index.html` 内容不变。

### P1-10 Gitee 更新白名单仍固定为历史仓库 `Zcy-sa/auth-pro`

- **证据**
  - `backend/handler/update.go` 常量 `giteeUpdateRepositoryPath`、`giteeUpdateAttachmentPath`、`giteeUpdateAPIReleasesPath` 都是 `/zcy-sa/auth-pro/...`。
  - `fetchGiteeLatestManifestURL` 拼附件地址时也写死 `Zcy-sa/auth-pro`。
  - 默认 `AUTO_PRO_UPDATE_URL` 为空时走 GitHub `maizll/auth-pro`，不会自动请求 Gitee。只有运维把更新地址指到该 Gitee 仓库时，这条白名单才会生效。
  - `backend/handler/update_test.go` 仍断言该历史仓库的包可以被接受。
- **影响**
  - 一旦启用 Gitee 更新地址，可安装的包来自历史 fork，而不是本仓库 `maizll/auth-pro`。历史仓库若仍可发 Release，就能向这台实例推更新。
- **修复形状**
  - 删除写死的 `Zcy-sa` 信任。Gitee 只作为运维显式配置的镜像，且 owner/repo 必须与配置一致，不能另有一个历史默认仓库。
- **建议测试**
  - 默认配置下，指向 `Zcy-sa/auth-pro` 的清单和包 URL 被拒绝。
  - 显式配置的镜像仓库只接受该 owner/repo 的 HTTPS 附件。

### P1-11 旧插件源安装 ZIP 时不核对 SHA256，并跟随任意重定向

- **证据**
  - `backend/handler/plugin_source.go` `AdminPluginDownload`：从清单取出 `downloadUrl` 后 `downloadPluginPackage` → `fetchPluginHTTP`。
  - `remotePluginEntry` 没有 SHA256 字段。`fetchPluginHTTP` 使用默认 `http.Client`，会跟随重定向，也不限制目标是公网 HTTPS。
  - 路由在 `superSecured`（仅超级管理员）。`README.md` 写明软件源允许内网地址，这是管理员主动添加源之后的行为。
  - 新源站登记路径 `verifyExternalPackageHTTP`（`source_package_host.go`）会核对 SHA256，和这条旧安装路径不是同一套。
- **影响**
  - 被改过的清单可以把 `downloadUrl` 指到内网或元数据地址，超级管理员一点「下载」就由服务器去取。
  - 清单即使带了校验和，安装前也不检查，包内容可在审核后被替换。
- **修复形状**
  - 下载后计算 SHA256，与清单不一致则不调用 `installPluginZIP`。
  - 禁止重定向到非 HTTPS，并拒绝链路本地、回环和云元数据网段。内网源改为显式开关。
- **建议测试**
  - 清单 SHA256 与响应体不一致时安装失败且插件目录无新文件。
  - `downloadUrl` 为 `http://127.0.0.1/` 或重定向到该地址时，客户端不被调用。

### P1-12 源站外链复核只要求 HTTPS，不拒绝内网地址

- **证据**
  - `backend/handler/source_station.go` `validateExternalHTTPS` 只检查协议是 `https`、路径不含 `..`。
  - `source_package_host.go` `verifyExternalPackageHTTP` 用该函数后直接 `GET`。重定向回调只拒绝离开 `https`，不解析目标 IP。
  - 开发者提交外链时会走到这里（`validatePackageForSubmit`）。本站托管 ZIP 则比对本地文件哈希，不发外网请求。
- **影响**
  - 已登录开发者可以让源站服务器请求 `https://10.x`、`https://169.254.169.254`（若该地址提供 TLS）或经 DNS 重新绑定到内网，用来探测内网服务。
- **修复形状**
  - 解析 DNS 后拒绝非全球单播地址，并在每次重定向后重新检查。连接时钉住已检查的 IP。
- **建议测试**
  - `https://127.0.0.1/pkg.zip` 与重定向到该主机的公网 URL 都返回错误，且不读取响应体。

### P1-13 首页按账号公开查询授权概况，且没有频率限制

- **证据**
  - `backend/main.go`：`GET /api/user-panel/license-query` 在用户登录组之外。
  - `backend/handler/license.go` `PublicUserLicenseQuery`：查询参数 `account` 或 `email` 匹配 `users.nickname` 或 `users.email`，返回应用名、套餐名、授权类型、状态、开通与到期时间。不需要登录或签名。
- **影响**
  - 知道昵称或邮箱即可列出该用户买过哪些应用、是否在有效期内。也可以用响应行数判断账号是否存在。
- **修复形状**
  - 改为登录后只查自己，或要求额外的查询口令 / 验证码，并加 IP 频率限制。公开字段收窄到「是否存在有效授权」，不要带套餐和到期日。
- **建议测试**
  - 未登录请求返回 401。
  - 登录用户只能看到自己的授权，传入他人邮箱仍只返回自己的列表。

### P1-14 源站结构迁移在每次启动时丢列，错误被忽略

- **证据**
  - `backend/main.go` 启动时调用 `handler.EnsureSourceStationSchema()`。
  - `backend/handler/source_station_store.go` 在 `CREATE TABLE IF NOT EXISTS` 之后，无条件执行一组 `ALTER`，其中包括 `DROP COLUMN file_path`、`published`、`preview_path` 等。循环是 `_, _ = db.Exec(statement)`。
  - 授权站点数迁移 `backend/migrate_activation_limit.go` 使用 `schema_migrations` 表，只在遗留列还在时 `DROP COLUMN max_activations`。源站这段没有同样的版本记录。
  - 安装脚本里的整库 `DROP TABLE` 见 P0-01，不要和这段混成一件事。
- **影响**
  - 进程每启动一次就对目录表做破坏性 `DROP COLUMN`。列一旦还在，其中的本地文件路径会被丢掉且无法从这条语句恢复。
  - 失败被吞掉，启动日志看不出哪一条 ALTER 没生效，后续请求可能按「列已经不存在」继续跑。
- **修复形状**
  - 把这些 ALTER 收成命名迁移，记入 `schema_migrations`，成功后不再执行。`DROP COLUMN` 前确认数据已迁到 `download_url`。
- **建议测试**
  - 连续两次 `Ensure`：第二次不应再发出 `DROP COLUMN`。
  - 迁移前插入 `file_path`，迁移后对应 `download_url` 仍能找到原值，或在值为空时迁移失败而不是删列。

## 已核对、不作为问题

- **CORS `Access-Control-Allow-Origin: *`**（`backend/middleware/cors.go`）。管理端使用 `Authorization: Bearer`，`frontend/.env` 里 `VITE_WITH_CREDENTIALS = false`。浏览器不会自动带上令牌，单独的 `*` 不能读走已登录会话。
- **易支付 V1 / V2 与支付宝当面付回调**。V1 `settleEpayCallback` 先验签再比金额，`settleRechargeOrder` 对订单 `SELECT ... FOR UPDATE`，金额不一致拒绝，`paid` 状态重复通知只提交事务。V2 `verifyEpayV2Sign` 用平台公钥。当面付 `ParseNotify` 先验 RSA2，金额进入同一套入账函数。`payment/alipayf2f/sign_test.go` 覆盖了篡改金额。没有单独的微信支付 V3 回调；微信作为易支付的 `type` 走上面的验签。
- **更新包 ZIP/tar 路径穿越**。`extractOnlineUpdatePackage` 拒绝绝对路径、`../` 和非普通文件。源站上传 ZIP 的拒绝用例在 `backend/handler/package_zip_test.go` 与 `source_station_package_test.go`（`../escape.txt`）。
- **校验接口必须返回 HTTP 401**。该接口是给 SDK 的公开接口，约定是 JSON `code`。缺少的是频率限制（P1-01），不是把 403 改成 HTTP 401。
- **MySQL 1213 死锁类**。`backend/handler/schema_ensure.go` 对结构补齐做了 1213/1205 重试，并有 `account_schema_ensure_test.go`。这次看到的购买并发问题是绝对值回写（P0-02），不是同一类元数据死锁。
- **安装接口的跨站调用**。未安装时，`InstallGuard` 会拒绝 `Origin` 与请求 Host 不同的浏览器调用。风险在锁文件丢失后的无 Origin 调用（P0-01），不在已安装状态。
