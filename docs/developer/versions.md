# 更新与多版本

## 1. 概述

| 项 | 说明 |
| --- | --- |
| 适用对象 | 已有目录项、需要发新包的开发者与管理员 |
| 前置条件 | 条目已存在；新包仍满足硬校验 |
| 与源站关系 | 已发布版本的包地址不可改写；请新增版本并审核 |

## 2. 目录结构

新版本仍是独立 ZIP，清单 `id` 必须与目录项标识一致，`version` 必须递增且不重复。

## 3. 清单字段表

版本对象（Release）：

| 字段名 | 类型 | 必填 | 默认 / 自动填充 | 中文说明 | 校验规则 | 示例值 |
| --- | --- | --- | --- | --- | --- | --- |
| version | string | 是 | 无 | 版本号 | 同清单 version，且与已有版本不冲突 | `"1.0.1"` |
| downloadUrl / templateUrl | string | 是 | 无 | 该版本地址 | 同打包规范 | HTTPS |
| sha256 | string | 是 | 无 | 该版本包校验和 | 64 位十六进制 | `cd…` |
| changelog | string | 否 | 空 | 本版本说明 | ≤2000 字 | `"修复下载"` |
| status | string | 系统写入 | `draft` / `pending` | 版本状态 | `draft` / `pending` / `published` / `deprecated` | `"pending"` |

条目级 `latestVersion` 指向当前对外版本。

## 4. kind / 分类绑定

发新版本不改变 kind。不要把插件版本改挂到 `home-template`，也不要把模板版本改挂到插件 extras（例如 key=`template` 的「模板」分类）。

## 5. 完整示例

登记新版本请求要点：`version`、`downloadUrl` 或 `templateUrl`、`sha256`、可选 `changelog`。

## 6. 开发者提交流程

1. 制作新 ZIP，id 不变，version 更新。
2. 在「版本」中登记新版本（draft / pending）。
3. 提交该版本审核。
4. 管理员通过后可「设为 latest」。
5. 弃用旧版本不会删除元数据，也不会远程卸载已安装实例。弃用后会从公开软件源目录清除，不再展示（若被弃用的是唯一或当前 latest 已发布版本）。

已上架条目的名称、下载地址或校验和可能被源站更正，**不会因此自动下架或退回待审核**。开发者改已发布版本的包地址时，仍须新增版本。

## 7. 常见错误与排查

| 现象 | 原因 | 改法 |
| --- | --- | --- |
| 无法改已发布版本地址 | 版本不可变 | 新增版本 |
| 上架失败 | 缺少 sha256 或 URL | 补齐后再上架 |
| 商店仍显示旧包 | latest 未切换 | 将新版本设为 latest 并确认条目 published |
