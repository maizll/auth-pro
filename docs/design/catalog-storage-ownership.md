# 软件目录归属与安装包存储（1.6.1 设计评审）

| 项 | 值 |
| --- | --- |
| 文档状态 | 1.6.1 锁定归属和存储契约。生命周期缺口见 §7：1.6.1 只补 P0，P1 进 1.6.2，P2 进 1.6.3 |
| 读者 | 实现工程师、后续存储管理（1.6.2） |
| 范围 | 目录条目和版本怎么挂在应用上；收费安装包存在哪；谁能改、谁能下；失败时不留半截数据 |
| 不在范围 | 免费条目改成私有仓库；买家流量改由本站转发；给开发者单独的仓库或令牌 |

本文把 1.6.1 里已经散着做的几件事收成同一套规则：外链和上传二选一、收费包进站长的一个私有仓库、开发者端同步、目录条目切换应用、历史「未归属」、删除应用时不要留下孤儿。后面的代码按本文改，不再各写各的。

和 `docs/design/software-source-enterprise.md` 的关系：审核规则（管理员可直发、开发者必审）、应用隔离、失败即拒绝，仍然有效。该文「源站不存源码」在收费仓库还没配好时，允许临时例外，见 §2.4。例外写在版本行上，不另开一套字段。

## 1. 数据模型与归属

### 1.1 五样东西各是什么

| 东西 | 存在哪 | 说明 |
| --- | --- | --- |
| 应用 | `apps` | 授权、套餐、客户端版本、软件目录都挂在它上面。身份是数字 `id`，对外还有 `app_key` |
| 目录条目 | `source_catalog_plugins` / `source_catalog_templates` | 一条插件或一条首页模板。`app_id` 表示属于哪个应用。最新对外地址仍写在条目的 `download_url` / `template_url`，这是「当前最新版」的线路格式，不是第二份存储 |
| 版本 | `source_catalog_plugin_versions` / `source_catalog_template_versions` | 每个版本一行。地址、校验码、存在哪个存储，以版本行为准 |
| 包文件 | 存储驱动后面的对象 | 本站磁盘上的文件，或 GitHub Release 上的附件。业务代码不直接拼路径 |
| 授权侧数据 | `licenses`、`license_plans`、`app_versions` 等 | 跟软件目录不是同一张表，但同样用 `app_id` 指向应用。订单通过授权或条目标识关联，订单表本身没有 `app_id` |

条目换应用时，只改条目的 `app_id`。版本、价格、地址、校验码、存储位置都留在原行上，跟着走。

插件的公开标识是主键 `id`，全表唯一，换应用不会和另一条插件撞标识。模板的公开标识是 `template_key`。目标应用里已经有同一个 `template_key` 时，整批拒绝，中文提示：`目标应用里已经有标识「…」`。已在目标应用上的条目跳过，不写库，避免「影响行数为 0」被当成找不到。

### 1.2 删除应用 = 归档，不留孤儿

用户点的「删除」从 1.6.1 起是归档，不是把 `apps` 行删掉。

- 写入 `apps.deleted_at`（非空即已归档），同时 `enabled = 0`。
- **不**删除 `apps` 行，因此 `id` 不会被新应用复用。
- **不**删除 `app_versions`，也**不**删这些版本的更新包文件。
- **不**删除授权、套餐、目录条目、私有包、GitHub 附件。
- 即使这个应用下面什么都没有，也归档，不硬删。空应用硬删再新建会复用不起 `id`，但历史授权若曾经指向它就会断；统一归档更简单。

目录条目还在时，必须二选一，否则接口返回 409：

1. **迁移并归档**：`migrateAppId` 指向另一个未归档的应用。条目的 `app_id` 改过去，再归档当前应用。不能迁到正在归档的这一条，也不能迁到已归档的应用。
2. **直接归档**：`archive=1`。条目仍挂在这个应用上。应用还在，所以这不是孤儿。目录里把该应用标成「已归档」，条目照常找得到。

两种都没给，中文说明条数，并同时提到可以迁移或直接归档。

已归档的应用仍出现在软件目录的应用列表里，`archived: true`。公开软件源 `index.json` 仍按 `app_key` 提供，避免已经装好的客户端突然读不到。新的登记、上传、切换目标不再接受已归档的应用。

「未归属（应用已删除）」只服务 1.6.1 之前已经发生的历史：`app_id <= 0`，或 `app_id` 在 `apps` 里根本没有这一行。新的归档**不会**再制造这种行。

### 1.3 外键与约束

目标约束都是 `ON DELETE RESTRICT`：只要还有子行指向这个应用，数据库拒绝硬删 `apps`。这是兜底。正常路径已经不再硬删。

| 约束名 | 表 | 列 |
| --- | --- | --- |
| `fk_source_catalog_plugin_app` | `source_catalog_plugins` | `app_id` |
| `fk_source_catalog_template_app` | `source_catalog_templates` | `app_id` |
| `fk_license_app` | `licenses` | `app_id` |
| `fk_license_plan_app` | `license_plans` | `app_id` |
| `fk_app_version_app` | `app_versions` | `app_id` |

`app_id = 0` 或指向已经不存在的应用，都算孤儿。MySQL 外键不能写成「仅当 `app_id > 0` 时检查」，所以**有孤儿就不加这条外键**。启动不因此失败，下次启动再试。全部孤儿清掉（站长把「未归属」绑回现存应用，或历史授权已经对上现存应用）之后，下一次启动加上约束。某一张表有孤儿，只跳过这一张，其他干净的表照常加。

订单表没有 `app_id`，不建这条外键。订单通过授权或条目标识保留。

列变更记入一次性迁移 `source_catalog_version_storage_v1`（版本上的存储字段）以及每次启动都执行的 `ensureAppDeletedAt`（`apps.deleted_at` 缺了就补，补过就跳过）。外键不记入一次性迁移：记成「已完成」之后，历史孤儿清掉也不会再补约束。

`apps.deleted_at`：

```sql
ALTER TABLE apps ADD COLUMN deleted_at DATETIME NULL DEFAULT NULL COMMENT '归档时间，非空表示已归档';
```

版本存储字段与回填见 §2.3。外键语句：

```sql
ALTER TABLE source_catalog_plugins
  ADD CONSTRAINT fk_source_catalog_plugin_app
  FOREIGN KEY (app_id) REFERENCES apps (id) ON DELETE RESTRICT;

ALTER TABLE source_catalog_templates
  ADD CONSTRAINT fk_source_catalog_template_app
  FOREIGN KEY (app_id) REFERENCES apps (id) ON DELETE RESTRICT;

ALTER TABLE licenses
  ADD CONSTRAINT fk_license_app
  FOREIGN KEY (app_id) REFERENCES apps (id) ON DELETE RESTRICT;

ALTER TABLE license_plans
  ADD CONSTRAINT fk_license_plan_app
  FOREIGN KEY (app_id) REFERENCES apps (id) ON DELETE RESTRICT;

ALTER TABLE app_versions
  ADD CONSTRAINT fk_app_version_app
  FOREIGN KEY (app_id) REFERENCES apps (id) ON DELETE RESTRICT;
```

运行时由 `ensureCatalogForeignKeys` 在孤儿数为 0 且约束尚不存在时执行。表不存在则跳过该条。

## 2. 包存储抽象

### 2.1 驱动接口

业务代码只认下面这个接口，不认 GitHub URL 怎么拼、磁盘目录在哪。

```text
PackageStorage
  Name() string
  Put(ctx, key, payload) (storedKey, error)
  SignedURL(ctx, key, ttl) (url, error)
  Delete(ctx, key) error
  Exists(ctx, key) (bool, error)
  List(ctx, prefix) ([]StoredObject, error)
```

`StoredObject` 至少有对象键。校验码以版本行上的 `sha256` 为准，列举接口可以不带校验码。

注册表按 `Name()` 查找。1.6.2 增加 Gitee、S3 时，只注册新的驱动，发布、下载、删除、健康检查都走同一条调用，不改目录业务。

### 2.2 1.6.1 实现的驱动

| 名称 | 1.6.1 | 对象键 | 行为 |
| --- | --- | --- | --- |
| `local` | 实现 | 文件名，例如 `0123….zip` | 未配置收费仓库时，收费包暂存在本站目录。买家下载仍走「授权换票」，因为票里有授权编号，驱动本身不知道是哪一张授权。`SignedURL` 对本地驱动返回明确错误，避免绕过换票 |
| `github` | 实现 | `owner/repo/tag/asset` 四段 | 站长配置的**一个**私有仓库、**一枚** Contents 读写令牌。`Put` 上传 Release 附件。`SignedURL` 用这枚令牌向 GitHub 换几分钟有效的地址，本站不转发文件字节 |
| `external` | 实现（只读分类） | 原始 `https://` 地址 | 免费条目的公开地址。`SignedURL` 原样返回该地址。`Put` / `Delete` 不支持。这样业务代码总能先分类再分支，而不是到处判断字符串前缀 |
| `gitee` / `s3` | 1.6.2 | 由该驱动定义 | 只加驱动和设置项 |

线路上仍用现有前缀，不在 1.6.1 把库存地址改写成另一种新格式：

| 库存字符串 | 驱动 | 对象键 |
| --- | --- | --- |
| `paid:{32位十六进制}.zip` | `local` | 文件名 |
| `github:owner/repo/tag/asset` | `github` | `owner/repo/tag/asset` |
| `https://…` | `external` | 整个 URL |

收费包写入：

- 仓库和令牌都已配置：`Put` 到 `github`。失败则把错误返回给调用方，**不**改存本站。
- 还没配置：`Put` 到 `local`，并在**管理端**用中文提醒。开发者端不显示这句。
- 用户粘贴的 GitHub 地址一律当公开 HTTPS 拉一次（每跳做 SSRF 检查），再按上面的规则放入 `github` 或 `local`。不用站长令牌去读别人的私有仓库。

买家：付费且驱动是 `github` 时，核销授权后 `SignedURL`。驱动是 `local` 时，仍签发本站下载票，下载前再核销一次。免费公开地址不走付费下载。

`Put` 的入参键用 `种类/条目标识/版本`，驱动返回真正落下去的对象键。GitHub 标签形如 `paid-{种类}-{标识}-{版本}`，附件名 `{标识}-{版本}.zip`。同一标签再次上传时，先删掉同名附件再传，结果覆盖，不留下两份。

`List` 在 GitHub 驱动上只取第一页 Release（最多 30 条），按前缀过滤。1.6.2 的存储管理界面负责翻页，业务代码不在 1.6.1 假装已经列全。

### 2.3 版本行记录存在哪

两个版本表增加：

```sql
ALTER TABLE source_catalog_plugin_versions
  ADD COLUMN storage_driver VARCHAR(20) NOT NULL DEFAULT '',
  ADD COLUMN object_key VARCHAR(500) NOT NULL DEFAULT '';

ALTER TABLE source_catalog_template_versions
  ADD COLUMN storage_driver VARCHAR(20) NOT NULL DEFAULT '',
  ADD COLUMN object_key VARCHAR(500) NOT NULL DEFAULT '';
```

`sha256` 原来就有。一次性迁移 `source_catalog_version_storage_v1` 按 `download_url` / `template_url` 回填驱动和对象键。读出版本时如果这两列仍空，用地址现算一遍，避免旧行在回填完成前读丢。

写入版本时必须同时写下这三样：`storage_driver`、`object_key`、`sha256`。条目上的地址只是最新版的线路格式，给公开目录和旧客户端看，不单独再存一套驱动名。

### 2.4 和「源站不存源码」怎么共存

企业设计里「只存元数据和 HTTPS 地址」仍然是目标。1.6.1 的例外只有一条：站长还没配好收费仓库时，收费 ZIP 暂存在本站，管理端用中文催促去配置。一旦仓库已配置，上传失败就失败，不能悄悄落回本站，否则同一条收费目录会有两种真相。

免费条目继续只存公开 HTTPS，本站不留 ZIP。

## 3. 权限

| 动作 | 管理员 | 开发者 | 买家 |
| --- | --- | --- | --- |
| 配置收费仓库、填写令牌 | 可以。令牌加密保存，接口和页面都不回显明文 | 不可以。没有设置入口，旧地址返回 404 | 不可以 |
| 看到「还没配仓库、包暂存在本站」 | 可以 | 不可以 | 不可以 |
| 看到仓库所有者和仓库名 | 可以 | 不可以。开发者看到的收费地址被收成「本站托管」，不出现 `github:` 或 `paid:` | 不可以 |
| 切换条目所属应用 | 任意条目，目标必须是未归档的现存应用 | 只能自己的条目，目标与入驻登记时同一个应用列表，且未归档。没有单独的「按应用授权」表；不额外发明一套更严的限制 | 不可以 |
| 编辑表单里改应用 | 不从编辑表单改。切换用专用动作，避免和「标识不能改」混在一起 | 编辑表单里的应用保持不可改。要换应用走「切换应用」 | 不可以 |
| 查看「未归属」 | 可以 | 自己的列表里，对不上现存应用的条目显示为「应用 #旧编号」 | 不可以 |
| 归档应用 | 可以。有目录条目时必须迁移或明确直接归档 | 不可以 | 不可以 |
| 恢复已归档应用 | 可以。清掉归档时间并重新启用。授权、版本、目录绑定都不动 | 不可以 | 不可以 |
| 把已弃用条目恢复为草稿 | 可以。不会自动上架，要再审核 | 不可以。没有这个按钮 | 不可以 |
| 下载收费包 | 不凭管理员身份绕过购买 | 不凭开发者身份拿到买家地址 | 仅当该授权允许下载这一条。地址是临时的，看不到令牌和仓库配置 |

同一应用上的标识冲突，管理员和开发者看到同一句中文，整批不改。

## 4. 审计、幂等、失败回滚

### 4.1 审计

| 动作 | `action` | 何时写 |
| --- | --- | --- |
| 切换应用 | `rebind_app` | 每一条真正改了 `app_id` 的条目。详情含从哪个应用到哪个应用。没变的不写 |
| 归档应用 | `archive_app` | 数据库归档成功之后。详情写明是迁移后归档、直接归档，还是下面没有目录条目 |
| 恢复应用 | `restore_app` | 清掉 `deleted_at` 并重新启用之后 |
| 弃用条目恢复为草稿 | `restore` | 仅当原状态是弃用、新状态是草稿。其它状态变化仍用原来的动作名 |

审计写失败不把已经成功的切换或归档再改回去。切换本身在改完 `app_id` 之后记；若中途某一条写库失败，前面已成功的条目保持新应用，接口返回错误，调用方看到失败后可以再提交。同一条再提交到同一目标是空操作（见下），所以重试是安全的。1.6.1 不把多条切换包进一个数据库事务：内存实现和 MySQL 实现共用同一套步骤，目标应用上的标识冲突在写库前全部检查完。

### 4.2 幂等

- 再次切换到当前应用：跳过，不报错，不写审计。
- 再次归档已经归档的应用：返回成功，文案「应用已归档」，不改授权和目录。
- 再次把同一版本传到 GitHub：同一标签上的同名附件先删再传，仓库里仍是一份。版本行覆盖为这一次的校验码和对象键。
- 外键确保、补列：列或约束已经在就跳过。

### 4.3 失败回滚

收费包发布的顺序固定为：校验 ZIP → 存储 `Put` → 成功后才写目录和版本。`Put` 失败时不写条目、不写版本、不把半截文件留成正式对象。

- GitHub 已配置但上传失败：返回中文错误，不调用本站 `Put`，不把条目改成 `paid:`。
- 本站 `Put` 中途失败：删掉临时文件，不返回对象键。
- 拉取公开地址失败：不写库。
- 归档接口在目录检查失败（409 / 400）时，不执行 `UPDATE apps`。
- 不因为「还没配令牌」而拒绝保存。那种情况走本站驱动，并只在管理端提醒。

## 5. 和 1.6.2 存储管理怎么接

1.6.2 里和存储有关的部分是「站长看得见、管得了存储」，不是再改归属规则。同一版还要做的购买、安装见 §7，不要提前塞进 1.6.1。

已经稳定、1.6.2 应直接沿用的：

- 驱动注册表和六个方法。Gitee、S3 各写一个类型并 `registerPackageStorage`，发布和买家下载不用改分支。
- 版本行上的 `storage_driver` + `object_key` + `sha256`。管理界面按这三列展示和筛选，不要再从地址字符串猜。
- 线路前缀 `paid:` / `github:` / `https://` 继续能读。新驱动可以有自己的前缀，但读取必须先 `classify`，禁止在业务里新增 `strings.HasPrefix`。
- 一个站长、一个收费仓库、一枚写令牌。1.6.2 若支持多个仓库，应做成「默认驱动 + 版本行记录实际驱动」，而不是回到「每个开发者一把令牌」。
- 归档、切换应用、未归属、外键补齐策略不变。
- `List` 的翻页、跨页删除、存储用量，放在管理界面。驱动的 `List(prefix)` 可以加分页参数，但不要把「删 GitHub 整个仓库」塞进目录发布流程。

1.6.2 不应做的返工：

- 不要把收费包再改成「开发者各自填令牌」。
- 不要为了 S3 重做条目的 `app_id` 或审核状态机。
- 不要把本地暂存当成和 GitHub 对等的长期方案去做成默认。它只是仓库未配置时的退路。
- 不要硬删应用。存储管理里删除的是对象，不是应用行。删对象前要看还有没有版本行引用该对象键。

## 6. 现有实现和本文冲突、必须收口的地方

下面这些是评审时对照代码的结论。1.6.1 按本文改完，才算同一套设计。

| 现状 | 冲突 | 收口 |
| --- | --- | --- |
| `AppDelete` 硬删 `apps`，并删除 `app_versions` 及其更新包 | 授权、目录、订单变成指空；前端还写「清除所有授权记录」，实际授权还在 | 改为只写 `deleted_at`。版本和授权保留。文案改为归档 |
| 有目录条目时只允许迁移后删除 | 迁移是可选项，但不是唯一安全做法。直接归档只要应用行还在，就不会变成未归属 | 409 时允许 `archive=1` 原地归档 |
| 全库没有外键 | 硬删或手工删行会留孤儿，而且不会在启动时被发现 | §1.3。有历史孤儿时跳过，不让启动失败 |
| 收费地址是裸字符串，`github:` / `paid:` 散落在发布、下载、健康检查里 | 1.6.2 加 Gitee/S3 必须改业务 | 收成 `PackageStorage`。发布和买家换地址走注册表 |
| 版本行只有地址和 `sha256`，没有驱动和对象键 | 存储管理无法回答「这个版本在哪个仓库」 | §2.3 两列 + 回填 |
| 「未归属」被当成删除应用后的正常归宿 | 新删除会继续制造找不到的条目 | 未归属只读历史。新归档的应用留在列表里并标「已归档」 |
| 切换目标没有拒绝已归档应用 | 条目会被绑到不能再登记的应用上，看起来像丢了 | 目标已归档时中文拒绝 |
| 开发者编辑接口禁止改 `app_id`，切换接口又允许 | 两套入口语义相反 | 保持编辑表单不可改应用；只有「切换应用」能改。文档写明，避免以后有人在编辑保存里再放开 |
| 企业设计写「源站不存源码」，收费包在未配置仓库时又落在本站 | 两句话同时当真会让人删掉本地退路，或让已配置仓库的失败又落回本地 | §2.4：退路仅限未配置；已配置则失败即失败 |
| 买家 GitHub 下载和本地换票各写一套判断 | 新驱动还要再复制 | 先分类再选驱动。本地仍换票，因为票绑定授权 |
| `bindSourceCatalogAppID` 对非管理员一改应用就 403 | 容易被误当成「开发者不能换应用」 | 那是编辑保存的保护。换应用只走 rebind |

不在本次收口里、但不要误改的：

- 不把支付宝当面付插件写进目录种子。
- 不改生产库。
- 付费条目对开发者（`developer_id > 0`）上架仍关闭，提示「付费条目暂不能上架」。
- 健康检查失败只标红和通知，不自动下架。本站暂存文件丢失也走同一轮检查，见 §7。

## 7. 插件和模板目录的生命周期

范围只限插件、模板这一套软件目录。不做消息总线、在线加密，也不重做系统监控。界面文字用中文。1.6.1 只补会丢数据、卡住人或有安全问题的 P0。P1、P2 不进这一版。

### 7.1 1.6.2（P1，这一版不做）

- 开发者收费上架，和买家购买、发放权益一起开放。不要只开上架、购买仍走不通。
- Gitee、S3 驱动，以及存储管理界面（按版本行上的驱动、对象键、校验码查看；`List` 翻页）。
- 客户端凭下载票安装、更新收费插件。公开清单继续不写收费地址。
- 本站暂存文件的健康结果放进存储界面，仍不自动下架。

### 7.2 1.6.3（P2，这一版不做）

- 比弃用更软的目录归档（条目先收起来，以后还能直接回到上架，而不是必须回到草稿再审）。
- 安装向导。
- 站内通知以外的提醒。不做消息总线，不做在线加密，不重做系统监控。
